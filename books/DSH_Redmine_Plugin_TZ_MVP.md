# Техническое задание: плагин Redmine для DeepSeek Harness (DSH)

**Документ:** функциональное и интерфейсное ТЗ для AI-агента-разработчика  
**Версия спецификации:** 1.0 (MVP)  
**Дата:** 25 октября 2026 г.  
**Язык интерфейса MVP:** русский  
**Статус:** согласованные продуктовые требования; технические детали интеграции подлежат сверке с установленной версией DSH и корпоративным Redmine  
**Тип результата:** отдельный устанавливаемый плагин DSH с интеграцией в Web UI  
**Важное ограничение:** этот документ не содержит кода реализации и не предписывает конкретные классы, компоненты или файловую структуру. Их определяет агент-разработчик после исследования исходников и возможностей целевой установки.

---

## 1. Цель и концепция

Разработать плагин, добавляющий в **глобальную навигацию Web UI DeepSeek Harness** самостоятельный раздел **Redmine**. Раздел подключается к **корпоративному экземпляру Redmine по персональному API-ключу**, отображает задачи, прежде всего **назначенные авторизованному пользователю**, и предоставляет удобный интерфейс для просмотра короткой информации, поиска, фильтрации, сортировки и ручного обновления.

Вторая ключевая функция — **передача выбранной задачи «В работу»**: пользователь заранее выбирает локальный workspace (проект DSH), после чего плагин создаёт **новую независимую сессию DSH** в этом workspace, формирует стартовый промпт по настраиваемому шаблону, подставляет ссылку на задачу и инициирует работу агента. Агент самостоятельно изучает задачу с помощью **уже существующих у пользователя MCP и skill**, а не через новую встроенную в панель систему чтения описаний и комментариев.

Базовый маршрут:

**Redmine (чтение) → список задач → выбор workspace → «В работу» → новая сессия DSH → промпт с URL задачи → агент и его существующие MCP/skills.**

**Плагин не изменяет данные Redmine.** Ни нажатие «В работу», ни запуск агента через плагин не должны автоматически менять статус, исполнителя, описание, комментарии, приоритет или иные поля Redmine.

### 1.1. Принципы

1. **Redmine в панели — диспетчер задач**, а не вторая полноценная копия Redmine.
2. **Redmine — только чтение** со стороны нового плагина; запись допускается исключительно в локальные настройки и сущности DSH.
3. **Один и тот же локальный каталог = один зарегистрированный проект DSH**, независимо от количества задач Redmine.
4. **Redmine-проект и проект/workspace DSH — разные сущности**; между ними разрешено запоминаемое пользовательское соответствие, но не требуется взаимно-однозначное отображение.
5. **Выбор workspace и «В работу» — две разные кнопки/операции.** Запуск не должен каждый раз показывать диалог выбора каталога.
6. Предпочтение отдаётся **штатным механизмам DSH** (плагины, слоты интерфейса, реестр workspace, контроллер сессий), а не их дублированию.
7. Список задач загружается прямыми **читающими REST-запросами на стороне Host**, без участия LLM и без вызовов Redmine MCP для построения UI.
8. Статусы, типы, категории и приоритеты **не фиксируются в коде по названию**: у корпоративного Redmine могут быть собственные справочники и workflow.

## 2. Исходные условия и границы

### 2.1. Известные вводные

- Используется DeepSeek Harness (DSH) с Web UI и возможностью установки собственных плагинов.
- Пользователь работает с несколькими проектами Redmine и несколькими локальными проектами DSH.
- Корпоративный Redmine, предположительно, развёрнут/обновлялся в **2022–2023 гг.**, но точная версия **не установлена**; нельзя требовать возможностей новейшего Redmine без проверки.
- Аутентификация Redmine — **API-ключ текущего пользователя**.
- У пользователя уже есть интеграционные **MCP и skill для чтения и изучения задачи агентом**. Новый плагин их не реализует и не подменяет.
- Локальные проекты DSH связываются с каталогами на файловой системе, доступными процессу DSH Host.

### 2.2. В MVP включено

- Подключение к одному корпоративному Redmine (URL + API-ключ) с тестом соединения.
- Глобальный раздел Redmine в Web UI DSH.
- Отображение списка задач текущего пользователя из всех доступных проектов; основной режим — «Мои задачи».
- Фильтры по проектам, статусам, типам задач (trackers), приоритетам, категориям; поиск по ID/названию; сортировка, пагинация.
- Кнопка **«Обновить»** (круговая стрелка) и первоначальная загрузка при открытии.
- Короткие метаданные задачи и переход в **оригинальный Web UI Redmine**.
- Отдельная кнопка **«Выбрать workspace» / «Изменить workspace»**, открывающая диалог выбора.
- Выбор уже зарегистрированного проекта DSH или существующей локальной директории с проверкой и регистрацией при отсутствии проекта.
- Сохранение выбора workspace для Redmine-проекта с возможностью ручного переопределения для отдельной задачи.
- Отдельная кнопка **«В работу»**, создающая новую DSH-сессию в выбранном workspace.
- Редактируемые шаблоны стартового промпта, подстановка сведений о задаче и автоматическая отправка промпта агенту.
- Связь задача Redmine ↔ созданные сессии DSH (с поддержкой более одной сессии для одной задачи).
- Устойчивость к ошибкам сети, проблемам доступа, удалению workspace, повторному нажатию и частичным сбоям запуска.

### 2.3. Не входит в MVP

- **Встроенная страница с полным текстом описания задачи** в панели DSH.
- **Показ комментариев/истории изменений/journals/вложений** в панели DSH.
- Редактирование задач Redmine, смена статуса, назначение ответственного, отправка комментария, логирование времени, запись файлов, создание/удаление задач.
- Автоматическая синхронизация статуса Redmine по факту работы агента или по результатам его сессии.
- Разработка нового MCP, нового skill или механизма чтения задач внутри агента.
- Постоянный фоновый опрос Redmine, push/webhook-синхронизация, уведомления о новых задачах.
- Массовый запуск задач, автоматическая постановка всех задач в очередь агенту.
- Управление многими экземплярами Redmine в одной установке; архитектура может предусмотреть расширяемость, но UI MVP рассчитан на одно подключение.
- Создание новых каталогов или репозиториев в файловой системе при выборе workspace.
- Обязательная разработка отдельного Redmine-плагина/расширения на стороне корпоративного Redmine.

## 3. Термины и сущности

| Термин | Значение |
|---|---|
| Redmine instance | Конкретный корпоративный сервер Redmine с базовым URL. |
| Redmine project | Серверный проект Redmine со своим ID, именем, задачами, категориями и правами. |
| Issue / задача | Задача Redmine с уникальным ID **в пределах экземпляра** и URL. |
| Текущий пользователь Redmine | Учётная запись, определяемая API-ключом. |
| Workspace / проект DSH | Локальный проект DSH, привязанный к **реальному абсолютному пути** на машине DSH Host. |
| Session / сессия DSH | Самостоятельная рабочая сессия/диалог агента с собственным контекстом, относящаяся к workspace. |
| «Выбрать workspace» | Установка локального рабочего проекта для конкретной задачи до запуска сессии. |
| «В работу» | Только создание и старт DSH-сессии; **не операция Redmine**. |
| Шаблон промпта | Редактируемый текст с подставляемыми переменными задачи. |
| Соответствие проектов | Сохраняемое предпочтение `экземпляр Redmine + пользователь + Redmine project ID → DSH workspace ID/путь`. |

**Правило идентичности:** не использовать имя проекта Redmine, заголовок задачи или отображаемое имя DSH workspace в качестве единственного ключа идентичности.

## 4. Роли и разрешения

- Основной пользователь — владелец ключа Redmine, работающий в DSH Web UI.
- Список проектов представляет **проекты, доступные этому Redmine-пользователю согласно API**, а не проекты организации вообще.
- Доступность проекта для просмотра не эквивалентна членству в проектной команде; режим «все доступные» не надо переименовывать в «все, где я участник» без отдельной проверки членства.
- Список задач по умолчанию ограничен **назначенными текущему пользователю** (не «созданными мной» и не «за которыми я наблюдаю»).
- Показывать только задачи, фактически разрешённые сервером данному API-ключу. Плагин не должен обходить ограничения прав.
- Если справочник категорий/статусов/проектов недоступен из-за прав, работать с доступными данными и ясно указывать ограничение; не выдавать отсутствие доступа за пустой список.

## 5. Глобальная панель Redmine

### 5.1. Размещение

- **Самостоятельный глобальный пункт «Redmine» в основной боковой навигации Web UI DSH** с иконкой задач/списка.
- Панель открывается **без привязки к текущей чат-сессии** и должна быть доступна при отсутствии открытой сессии.
- Не использовать для основного интерфейса правую панель, привязанную к конкретной сессии: она предназначена для другого контекста.
- Предпочтительно пользоваться существующим глобальным механизмом Web UI slots / layout DSH, следуя возможностям установленной версии.

### 5.2. Заголовок панели

В верхней области:

- Заголовок **Redmine** / подзаголовок **Мои задачи**.
- Краткое указание текущего подключения или имени пользователя, если доступно.
- **Кнопка «Обновить» с иконкой круговой стрелки** — видимая, с подсказкой и состоянием загрузки.
- Доступ к настройкам подключения и шаблонов через отдельную команду/иконку.
- Индикатор «Только чтение» допускается как ненавязчивая подсказка, но не должен занимать центральное место.

### 5.3. Список задач

Каждая строка/карточка содержит:

| Поле | Требование |
|---|---|
| Номер задачи | Обязательно, формат `#1842`, визуально различим. |
| Краткое название (subject) | Обязательно; ограничение длины в списке с доступом к полному заголовку. |
| Проект Redmine | Обязательно; отображать человекочитаемое имя, хранить ID. |
| Статус | Обязательно; отображать исходное имя из Redmine. |
| Тип/трекер | Отображать при наличии. |
| Приоритет | Отображать при наличии. |
| Категория | Отображать при наличии, отсутствие обозначать нейтрально. |
| Исполнитель | Опционально в строке (особенно если пользователь изменит режим исполнителя). |
| Дата последнего обновления | Отображать при наличии, использовать для сортировки. |
| Workspace DSH | Отображать выбранный каталог или состояние «Не выбран». |
| Действия | «Выбрать/Изменить workspace», «В работу», «Открыть в Redmine»; при наличии — «Открыть сессию». |

**Не показывать** тело описания, комментарии, историю и содержимое вложений. API может включать некоторые такие поля в стандартный ответ; плагин не должен использовать их для отдельного UI, хранения/индексации или передачи агенту в стартовом промпте без явного изменения ТЗ.

### 5.4. Варианты представления

- Основной вариант MVP — **компактный список/таблица или карточки**, адаптирующиеся к ширине панели.
- Возможен переключатель «компактно/подробно» как UX-улучшение, если не усложняет MVP. «Подробно» означает **больше метаданных**, а не тело задачи.
- Полный заголовок задачи доступен по наведению/фокусу или через обычное отображение без обрезки, но это **не отдельный экран деталей**.
- Подсветка выбранной записи не должна путаться с фактом «задача запущена агентом».
- Клик по номеру или действие «Открыть в Redmine» открывает исходную задачу в браузере; карточка целиком не должна неожиданно запускать агента.

## 6. Фильтры, поиск и сортировка

### 6.1. Набор фильтров MVP

| Фильтр | Стартовое значение | Требование |
|---|---|---|
| Исполнитель | **Я** | Базовый режим `assigned_to_id=me` либо эквивалент текущего пользователя; в MVP гарантировать «Мои задачи». Расширение на других исполнителей — не обязательное. |
| Проект | **Все доступные** | Один, несколько или все доступные проекты; предпочтительно multi-select с поиском. |
| Статус | **Все открытые** | Группы «Все открытые», «Все статусы», «Закрытые» и конкретные серверные статусы. |
| Тип (Tracker) | **Все** | Значения из справочника Redmine. |
| Приоритет | **Все** | Значения из справочника Redmine. |
| Категория | **Все** | Значения с учётом выбранного проекта или проектов. |
| Поиск | Пусто | По ID и названию задачи, с понятной областью поиска. |
| Сортировка | **Обновлено: новые сначала** | Минимум сортировка по времени обновления (в обе стороны), дополнительно по ID/приоритету/названию, если доступно. |

### 6.2. Уточнения по проектам

1. Пользователь может иметь доступ к множеству проектов; показывать **все страницы** результата API, а не только первые 25/50 элементов.
2. **«Все проекты»** охватывает доступные по правам пользователя проекты, в отношении которых сервер разрешает запрос задач; фильтрация по исполнителю «Я» при этом сохраняется.
3. Выбор нескольких проектов не должен неожиданно переключать исполнителя или статус.
4. При изменении проекта обновлять применимость категорий и других проектно-зависимых справочников; не оставлять скрытую невалидную категорию.
5. Когда выбрано несколько проектов, категория должна быть однозначно интерпретирована по ID с учётом проекта; одинаковые названия категорий в разных проектах **не означают один объект**.
6. Если выбран проект, в котором у пользователя нет доступных задач, показывать пустой результат, а не ошибку.

### 6.3. Уточнения по статусам

- Не считать названия «Новая», «В работе», «Обратная связь», «Закрыта» фиксированным международным стандартом: в компании названия и ID могут быть изменены.
- Группы «Открытые»/«Закрытые» определять по возможностям Redmine и данным статусов, а не сопоставлением по русским строкам.
- При выборе одного статуса показывать его точное имя, при множественном выборе — краткое перечисление/количество и возможность очистки.
- При отсутствии отдельного справочника использовать доступные серверные сведения и фиксировать деградацию интерфейса.

### 6.4. Семантика поиска

- Поиск по числовому `#ID` и по фрагменту заголовка, без учёта регистра для текста.
- Поиск работает совместно с фильтрами, не отменяет текущий проект/исполнителя/статус.
- **Нельзя незаметно искать только в текущей странице, если UI обещает поиск по всем отфильтрованным задачам.**
- Агент-разработчик обязан изучить возможности поискового endpoint старого Redmine; если серверного поиска по заголовкам нет или он не удовлетворяет требованиям, реализовать корректную контролируемую альтернативу (например, выборку результатов фильтра с последующим поиском по полному доступному набору с лимитами и явным сообщением о неполноте при достижении предела).
- При ограниченном/частичном поиске интерфейс **явно сообщает область поиска** и не показывает ложный «0 результатов» при неполной выборке.
- Избегать отдельной загрузки описаний/комментариев ради поиска.
- Задержка ввода (debounce) допустима, чтобы не отправлять запрос на каждый символ.

### 6.5. Пагинация и сортировка

- Серверная пагинация везде, где поддерживается, в том числе для списка проектов; навигация по страницам или «Загрузить ещё».
- Корректно использовать `total_count`, `offset`, `limit` (если присутствуют), понимать ограничение серверного максимума `limit`.
- Выбор фильтра или сортировки возвращает на первую страницу; при ручном обновлении сохранять контекст, если страница всё ещё существует, иначе перейти на последнюю допустимую/первую.
- Не показывать дубли при переходе между страницами, даже если данные обновились в Redmine; учитывать изменяемость выдачи.
- Сортировка должна быть глобально корректной, а не перестановкой одной страницы при обещанной общей сортировке.
- Сохранять выбранные фильтры и сортировку при переключении на другую панель DSH и возвращении. Желательно — между перезапусками интерфейса.
- Кнопка **«Сбросить фильтры»** восстанавливает значения по умолчанию.

## 7. Загрузка и кнопка «Обновить»

### 7.1. Первоначальная загрузка

- При первом открытии Redmine-панели после настройки соединения запрашиваются необходимые справочники и список задач с фильтрами по умолчанию.
- Если настройки подключения ещё не заполнены — показать содержательное пустое состояние и кнопку «Настроить Redmine».
- Повторный вход в панель может использовать уже загруженное состояние и предложить ручное обновление. Обязательного фонового polling нет.

### 7.2. Ручное обновление

- Явная кнопка **`⟳ Обновить`**, размещённая в правой части заголовка.
- По нажатию повторно получать **актуальный** список для текущих фильтров и, если требуется, актуализировать справочники.
- Показывать spinner/вращение и состояние недоступности повторного нажатия на время одного запроса.
- Не стирать значения фильтров, поиска, сортировки и выбранные workspace.
- При успехе обновить список, количество элементов, время последнего успешного обновления (если отображается).
- При ошибке **сохранить предыдущие данные**, отметить их как потенциально устаревшие и предложить повторить операцию.
- Если начался новый запрос после смены фильтров, поздний ответ предыдущего запроса не должен заменять результаты более нового.
- **Нет автоматического редактирования задач, запуска агентов или фонового изменения статусов после обновления.**

## 8. Выбор workspace — отдельное действие

### 8.1. UI и принцип

У каждой задачи есть отдельная кнопка **«Выбрать workspace»**, а после выбора — **«Изменить workspace»**. Это отдельное действие, **не часть модального диалога кнопки «В работу»**.

Кнопка открывает диалог, предлагающий:

**Вариант A: существующий локальный проект DSH.** Список уже зарегистрированных workspace с названием и абсолютным путём; поиск и выбор одного проекта.

**Вариант B: другая существующая директория.** Вызов штатного файлового/директорного пикера DSH, где доступно; иначе функционально эквивалентный безопасный выбор директории, поддерживаемый целевой Web/Host-средой. Ввод/выбор должен соответствовать каталогу **на машине, где работает DSH Host**, а не обязательно на устройстве, где открыт браузер.

После выбора директории:

1. Проверить, что это абсолютный существующий каталог, а не файл; что Host имеет необходимые права.
2. Нормализовать/канонизировать путь с учётом ОС и штатных правил DSH.
3. Спросить реестр DSH, существует ли проект для **этой же директории**.
4. **Если существует** — переиспользовать зарегистрированный workspace и его ID.
5. **Если не существует** — зарегистрировать существующую директорию как новый локальный проект DSH, затем использовать его ID.
6. Показать пользователю итоговый workspace, закрыть диалог по подтверждению.
7. Не создавать копию проекта и не дублировать запись при повторном выборе того же пути.

**Папку на диске плагин не создаёт.** «Создать проект DSH» означает зарегистрировать выбранную существующую директорию в системе проектов DSH.

### 8.2. Идентичность и защита от дублей

- Сравнение ведётся по реальному каноническому пути, **не по имени** проекта, названию каталога, регистру строки без учёта особенностей ОС или ID Redmine-проекта.
- Если две разные директории имеют одинаковое отображаемое имя — это разные workspace.
- Повторная регистрация того же каталога возвращает/использует прежний проект.
- Учитывать символьные ссылки, регистр путей, завершающий слэш, корень диска, сетевые каталоги и недоступные каталоги так, как делает установленная версия реестра DSH.
- Если каталог ранее был зарегистрирован, но регистрация удалена, его можно зарегистрировать вновь, не изменяя файловое содержимое.
- Если локальный каталог удалён/стал недоступен, не делать вид, что он пригоден для запуска; предложить выбрать другой.
- В ходе разработки проверить, что сохранённая привязка workspace к сессии соответствует именно её рабочему каталогу.

### 8.3. Сохранение соответствий

Система запоминает предпочтение **для Redmine-проекта**:

`Redmine base URL + Redmine user identity + Redmine project ID → DSH workspace ID + canonical path (для перепроверки)`.

- После первого явного выбора пользователь может отметить **«Запомнить выбор для этого проекта Redmine»**; рекомендовано включить по умолчанию с возможностью выключить.
- При открытии другой задачи того же Redmine-проекта сохранённый workspace **автоматически предлагается/подставляется**, если существует и валиден.
- Пользователь в любой момент может нажать **«Изменить workspace»** и переопределить каталог для текущей задачи.
- Разные задачи одного Redmine-проекта могут выполняться в **разных локальных репозиториях**; выбор для задачи имеет приоритет над предпочтением проекта.
- При замене предпочтения проекта не менять уже существующие сессии или запомненные индивидуальные переопределения, если пользователь явно не подтвердил иное.
- При удалённом workspace ID попытаться разрешить сохранённый canonical path через реестр; при отсутствии регистрации допустимо предложить повторное подтверждение/регистрацию, но **не создавать проект без явного выбора или подтверждения пользователя**.
- Не связывать рабочие каталоги между разными учётными записями Redmine по одному лишь названию проекта.

### 8.4. До и после выбора

- До выбора: текст **«Workspace не выбран»**, доступна кнопка **«Выбрать workspace»**, **«В работу» неактивна**.
- После выбора: отображаются название workspace и путь; кнопка меняется на **«Изменить workspace»**, **«В работу» становится активной**, если остальные условия готовы.
- Если сохранённое соответствие валидно: workspace считается выбранным, диалог можно не открывать повторно.
- Изменение workspace не запускает агента и не влияет на Redmine.

## 9. Действие «В работу»

### 9.1. Стандартный сценарий

**Предусловия:** настроен Redmine; задача доступна; для задачи определён валидный workspace; есть действительный шаблон стартового промпта и необходимые сервисы создания сессии.

1. Пользователь нажимает **«В работу»** на карточке или через её контекстное меню.
2. Плагин берёт выбранный workspace и **повторно проверяет его пригодность**.
3. Формирует промпт из выбранного пользовательского шаблона; подставляет URL, ID, название и проект задачи.
4. Создаёт **новую обычную независимую DSH-сессию**, связанную с выбранным workspace.
5. Передаёт сформированный промпт как первоначальное пользовательское сообщение в новую сессию и **инициирует запуск агента**.
6. Сохраняет связь «экземпляр Redmine/задача → DSH-сессия».
7. Открывает созданную сессию в интерфейсе DSH; пользователь видит прогресс и может продолжить работу.

**Важно:** «новая сессия» не означает «новый DSH-проект». Проект создаётся/регистрируется только на стадии выбора директории, если он отсутствовал. Это также не означает порождение подагента внутри прежней сессии.

### 9.2. Повторный запуск той же задачи

- Для одной задачи Redmine допустимо иметь **несколько независимых сессий DSH**.
- Каждое **новое осознанное** нажатие «В работу» после завершения предыдущей операции может создать новую сессию.
- UI может показывать маркер **«Есть сессии: N»** или действие **«Открыть последнюю сессию»**.
- Открытие существующей сессии — отдельное действие, **не скрытая замена** команды «В работу».
- Быстрые двойные нажатия, повторы на фоне ожидания ответа или сетевые ретраи не должны создавать две сессии от одного пользовательского запуска.
- Если новая сессия уже создана, но отправка промпта завершилась ошибкой, сохранять её ID и показывать варианты «Открыть созданную сессию», «Повторить отправку»; **не создавать молча вторую**.
- Если создание сессии не подтвердилось из-за потери ответа, выполнить безопасную проверку/восстановление статуса операции, прежде чем повторять создание.

### 9.3. Поведение запуска

- Базовый режим: **промпт отправляется автоматически**, без отдельного подтверждения после нажатия «В работу».
- Не открывать повторно диалог выбора workspace, если workspace уже валиден.
- Не запускать сессию без workspace.
- Не менять Redmine-задачу на «В работе»: это название кнопки в DSH, а не статус Redmine.
- Доступность MCP и skill на момент запуска не является обязательным условием для отображения списка Redmine; отсутствие их в агентной среде следует корректно сообщить или дать агенту обработать, **не подменяя их кодом плагина**.
- При необходимости существующие механизмы разрешений DSH на действия агента должны продолжать работать без обхода.

## 10. Шаблоны промптов

### 10.1. Функциональность

- В настройках плагина есть раздел **«Шаблоны запуска»**.
- Пользователь может просматривать, создавать, редактировать, переименовывать, выбирать основной и удалять собственные шаблоны (последний работоспособный шаблон нельзя удалить без замены).
- По умолчанию доступен как минимум один **редактируемый** шаблон «Изучить задачу».
- В карточке задачи допускается меню «В работу с шаблоном…», если шаблонов несколько; простая кнопка «В работу» использует шаблон по умолчанию.
- Перед запуском проверяются синтаксис переменных, непустой результат и возможность сформировать URL.
- В сообщении агенту передаётся **результат подстановки**, а не текст с необработанными плейсхолдерами.

### 10.2. Минимальные плейсхолдеры

| Переменная | Значение |
|---|---|
| `{{issue.id}}` | Номер задачи. |
| `{{issue.url}}` | Каноническая браузерная ссылка на задачу Redmine. |
| `{{issue.subject}}` | Краткий заголовок. |
| `{{project.id}}` | ID проекта Redmine. |
| `{{project.name}}` | Имя проекта Redmine. |

Дополнительные переменные (`status`, `tracker`, `priority`) могут появиться, если реально нужны; их доступность/поведение при отсутствии данных должны быть документированы. **Не включать** `description`, `comments`, API-ключ или другие секреты в стандартный набор переменных.

### 10.3. Пример стартового шаблона (не программный код)

> Изучи задачу Redmine `{{issue.url}}` (№ `{{issue.id}}`, проект `{{project.name}}`). Используй уже доступные тебе Redmine MCP и соответствующий skill, чтобы самостоятельно получить описание и необходимые связанные сведения. Изучи требования в контексте текущего рабочего каталога DSH. Составь краткий анализ и план решения, обозначь неясности и риски. Не изменяй Redmine. Не приступай к изменению кода, пока пользователь не подтвердит план.

Этот текст — **начальное предложение**, не обязательный системный промпт. Пользователь вправе заменить его инструкцией на реализацию, анализ, отладку или иной сценарий. По умолчанию выбран безопасный аналитический сценарий.

### 10.4. Безопасная подстановка

- Название задачи и другие данные Redmine — **не доверенные инструкции**; включать их как данные, не позволяя им менять политику запуска или захватывать структуру шаблона.
- API-ключ никогда не является частью шаблона.
- Ссылка формируется на разрешённый сконфигурированный Redmine-сервер, а не на произвольный домен из данных задачи.
- Показывать пользователю превью сформированного сообщения в настройках (опционально, но желательно); сам запуск по базовому UX однокнопочный.

## 11. Подключение к корпоративному Redmine

### 11.1. Настройки

- **Базовый URL** корпоративного Redmine; поддержка установки под подпутём сайта, если такой путь применяется в компании.
- **Персональный API-ключ**, ввод скрыт, с возможностью заменить или очистить.
- Кнопка **«Проверить соединение»**: проверяет доступность сервера, ключ и возвращает идентичность текущего пользователя, не изменяя данные Redmine.
- По результату показывать понятные сообщения: успешно/нет сети/неверный ключ/доступ запрещён/REST API выключен/неверный URL/проблема TLS.
- Допускается поддержка системного прокси и корпоративного доверенного CA. **Не отключать проверку TLS по умолчанию.**
- Состояние ключа «Настроен / Не настроен», без возможности прочитать его обратно в открытом виде после сохранения.

### 11.2. Redmine старых версий

Не полагаться на Redmine API-функции, добавленные только в новых ветках. На этапе исследования подтвердить по фактической установке, что работают:

| Читающая операция | Для чего нужна |
|---|---|
| `/users/current.json` | Получить текущего пользователя по ключу. |
| `/projects.json` | Перечислить доступные проекты. |
| `/issues.json` | Получить список задач, в том числе `assigned_to_id=me`. |
| `/issue_statuses.json` | Получить статусы и их атрибуты. |
| `/trackers.json` | Получить типы/трекеры. |
| `/enumerations/issue_priorities.json` | Получить приоритеты. |
| `/projects/{id}/issue_categories.json` | Получить категории конкретного проекта. |

Для поиска по названию и сложных сочетаний фильтров нужна **отдельная проверка** фактической версии и прав. Нельзя считать наличие endpoint поиска гарантией, что он поддерживает все желаемые операторы и совместно учитывает фильтры списка.

### 11.3. Запросы и отказоустойчивость

- Использовать только **HTTP GET** для Redmine; при наличии транспортных проверок типа `HEAD` они не должны менять данные. **Никаких `POST`, `PUT`, `PATCH`, `DELETE` к Redmine в плагине.**
- API-ключ передавать безопасно на стороне Host, предпочтительно через заголовок **`X-Redmine-API-Key`**, не в query string, чтобы он не попал в историю и журналы URL.
- Различать ошибки сети, аутентификации, разрешений, отсутствующего ресурса, ограничений частоты запросов и некорректного ответа.
- Таймауты, отмена устаревших запросов и ограниченные повторы допустимы для безопасных GET; учитывать корпоративную нагрузку.
- Не запускать параллельно чрезмерное количество запросов категорий по всем проектам; получать по необходимости, кэшировать/обновлять при смене фильтров.
- Корректно декодировать JSON и обработать отсутствие необязательных полей, разные названия статусов и специфические настройки Redmine.
- Если справочник временно недоступен, не блокировать отображение уже полученных задач без необходимости.

### 11.4. Истинное значение read-only

Запрет записи относится **к новому плагину** и ко всем его REST-запросам. Запуск агента через существующий MCP сам по себе может иметь доступ к пишущим инструментам, **если они уже выданы агенту пользователем**. Поэтому:

1. Стартовый шаблон явно запрещает изменения Redmine по умолчанию.
2. Для технически строгой гарантии «никакого изменения Redmine даже агентом» на целевой установке требуется **отдельно ограничить агентные Redmine MCP-инструменты режимом чтения** / ключом с минимально возможными правами / политикой разрешений DSH. Это вопрос настройки существующей интеграции, не разработки MCP в данном MVP.
3. Не утверждать в документации, что плагин технически запретил любому внешнему MCP писать в Redmine, если фактически такое ограничение не настроено.

## 12. Логическая архитектура без реализации

### 12.1. Границы компонентов

1. **Web UI расширение:** глобальная панель, фильтры, список задач, диалоги выбора workspace, настройки, индикация состояний.
2. **Интеграция Host ↔ Redmine:** хранит настройки подключения/ключ, отправляет читающие REST-запросы, нормализует данные Redmine и ошибки.
3. **Слой предпочтений:** хранит фильтры, шаблоны, соответствия проектов и индивидуальные переопределения, связи задач с сессиями.
4. **Адаптер к штатным workspace DSH:** перечисляет, выбирает, находит и при необходимости регистрирует каталог.
5. **Адаптер к штатным сессиям DSH:** создаёт новую сессию, отправляет сформированный промпт, переводит интерфейс на сессию.
6. **Существующий агентный runtime + MCP/skills:** отвечает за чтение полной задачи и выполнение работы после запуска.

**Не добавлять второй реестр локальных проектов, собственную систему сессий или HTTP-прокси с открытым API-ключом для браузера.**

### 12.2. Данные и сохранение

Минимально сохраняемые логические данные:

| Данные | Хранение / принцип |
|---|---|
| Redmine URL | Конфигурация плагина. |
| API-ключ | Только безопасное Host-хранилище секретов/credentials DSH, не Web Storage и не логи. |
| Текущий Redmine user ID | Результат проверки подключения, для изоляции настроек. |
| Последние фильтры/сортировка | Пользовательские настройки UI. |
| Шаблоны промптов + основной шаблон | Настройки пользователя. |
| Redmine project → workspace | Устойчивое предпочтение с перепроверкой актуальности. |
| Issue → индивидуальный workspace | Переопределение выбора для конкретной задачи, если есть. |
| Issue → DSH session IDs | История запусков, допускает множество сессий. |
| Время последней успешной загрузки | Необязательные метаданные состояния. |

Связи с Redmine-данными должны иметь namespace по **нормализованному URL сервера и ID текущего пользователя**. При смене URL или ключа нельзя автоматически применять чужие соответствия и кэш задач.

Сохранённые ссылки на сессии DSH не должны препятствовать удалению/архивации сессий штатными средствами DSH. Если сессия более недоступна, показывать корректное состояние, а не нерабочую команду.

### 12.3. Предварительная проверка DSH перед кодированием

Агент-разработчик **обязан сверить фактически установленную версию** и доступные интерфейсы, поскольку upstream мог измениться. Предварительно известные штатные механизмы:

- **Cordis** — плагинная архитектура DSH.
- Глобальные UI slots для пункта в боковой навигации и главной панели (в актуальной документации фигурируют `sidebar.panellist` и `main`).
- `ctx.workspaceRegistry`: получение списка проектов, разрешение по пути, регистрация существующей директории.
- Workspace Controller/UI Workspace: штатный выбор каталога, где поддерживается.
- Session Controller: штатное создание обычной сессии и отправка начального промпта.

Это **ориентиры для исследования, а не приказ копировать конкретный API из документации другой версии**. Нужно выбрать поддерживаемый официально путь расширения, чтобы плагин был отключаемым и не требовал несанкционированной модификации ядра DSH.

## 13. Интерфейс: текстовые (символьные) макеты

- Сохранять визуальную стилистику DSH (светлая/тёмная тема, типографика, стандартные состояния кнопок, hover/focus).
- Поддерживать навигацию клавиатурой, подсказки и явные текстовые названия действий; иконка refresh не должна быть единственным доступным названием.
- Адаптировать расположение фильтров и действий под узкую ширину; не обрезать первичные действия без альтернативы.
- Для неподдерживаемых фильтров/операций показывать понятное ограничение, а не неработающую кнопку без объяснения.
- Сообщения ошибок — без секретов, внутренних стеков и полного текста HTTP-заголовков.

## 14. Пользовательские сценарии (Use Cases)

### UC-01. Первое подключение

1. Открыть раздел Redmine → увидеть приглашение настройки.
2. Ввести URL и API-ключ → «Проверить соединение».
3. При успехе увидеть текущего пользователя; сохранить конфигурацию.
4. При открытии панели — загрузка списка назначенных задач из всех доступных проектов с открытыми статусами.

### UC-02. Фильтрация

1. Открыть панель и выбрать несколько проектов.
2. Выбрать один или несколько статусов, тип, приоритет и подходящую категорию.
3. Ввести фрагмент названия или номер задачи.
4. Получить корректно отфильтрованный и отсортированный список; при переходе между страницами условия не теряются.
5. Перейти в другую панель DSH и вернуться → фильтры сохранены.

### UC-03. Ручное обновление

1. Пользователь установил фильтры и находится на определённой странице.
2. Нажал **`↻ Обновить`**.
3. Увидел индикатор загрузки; лишние параллельные нажатия не запускают повторные запросы.
4. После успеха увидел актуальный список, **не потеряв выбранные фильтры и workspace**.
5. При сетевой ошибке увидел старый список с указанием устаревания и кнопку повтора.

### UC-04. Выбор существующего workspace

1. Пользователь видит задачу #1842.
2. Нажимает отдельную кнопку **«Выбрать workspace»**.
3. В диалоге выбирает уже зарегистрированный проект DSH `D:\Projects\backend`.
4. Подтверждает выбор; на карточке отображается выбранный workspace.
5. Количество проектов DSH не увеличилось.

### UC-05. Выбор незарегистрированной директории

1. Пользователь открывает диалог через «Выбрать workspace».
2. Выбирает существующий каталог `D:\Projects\new-service`.
3. Плагин проверяет путь и обнаруживает отсутствие зарегистрированного workspace.
4. Пользователь подтверждает выбор; каталог регистрируется как новый проект DSH.
5. Карточка задачи ссылается на созданный проект; повторение того же выбора **не создаёт дубль**.

### UC-06. Использование сохранённого соответствия

1. Пользователь однажды связал Redmine-проект `Backend API` с `D:\Projects\backend` и сохранил выбор.
2. Открыл другую задачу из `Backend API`.
3. На карточке автоматически отображается валидный ранее выбранный workspace.
4. При необходимости пользователь нажимает «Изменить workspace» и выбирает другой каталог только для этой задачи.

### UC-07. Запуск «В работу»

1. Выбрана задача #1842 «Исправить расчёт лимитов»; workspace `D:\Projects\backend` валиден.
2. Пользователь нажимает **«В работу»** — не вызывая диалог workspace.
3. Создаётся **одна новая** сессия DSH в **существующем** локальном проекте.
4. В сессию автоматически отправляется стартовый промпт с **URL именно задачи #1842**.
5. Сессия открывается, агент получает возможность использовать ранее настроенные MCP/skill.
6. В Redmine **не происходит ни одной операции записи**.

### UC-08. Повторное использование задачи и сессий

1. Задача #1842 уже запускалась в DSH ранее.
2. Пользователь может «Открыть последнюю сессию» без создания новой.
3. При отдельном новом «В работу» создаётся ещё одна независимая сессия в выбранном workspace.
4. Двойной клик по одному запуску не создаёт двух сессий.

### UC-09. Неактуальный workspace

1. Сохранённый для Redmine-проекта workspace удалён из реестра DSH.
2. Плагин повторно проверяет ID/путь; не использует слепо устаревший ID.
3. Предлагает выбрать/подтвердить подходящий существующий каталог и при необходимости зарегистрировать его.
4. Не создаёт несуществующую папку и не запускает сессию с недействительным cwd.

### UC-10. Частичный сбой запуска

1. DSH-сессия создана, но промпт не отправился из-за ошибки.
2. UI сообщает: «Сессия создана, запуск не завершён».
3. Пользователь может открыть созданную сессию или повторить отправку.
4. Не появляется вторая дублирующая сессия от того же действия.

## 15. Матрица ошибок

| Ситуация | Требуемое поведение |
|---|---|
| URL/ключ не заданы | Состояние настройки, отсутствие сетевых запросов без подключения. |
| API-ключ неправильный / просрочен | Явная ошибка авторизации, предложение заменить ключ. |
| 403 / нет доступа | Показ сообщения о правах, не считать это пустым списком. |
| REST API Redmine отключён | Подсказка о необходимости включения администратором, без попыток обхода. |
| Redmine не отвечает / таймаут | Сохранять ранее загруженные данные, кнопка повтора. |
| Неподдерживаемый фильтр/endpoint | Совместимый вариант/понятное ограничение, без бесконечных повторов. |
| В Redmine нет моих задач | Корректный пустой результат. |
| Справочник категорий отсутствует | Остальные фильтры работают; категория отмечена как недоступная. |
| Изменились права / проект скрыт | Обновить список доступных проектов, удалить из активного фильтра недоступную опцию. |
| Директория workspace не существует | Не запускать; предложить другую. |
| Путь уже зарегистрирован в DSH | Использовать существующий проект, не создавать новый. |
| DSH не может зарегистрировать каталог | Показать ошибку, не отмечать его как выбранный без успешной регистрации. |
| Сервис сессий DSH недоступен | «В работу» недоступна или завершается понятной ошибкой без частичной потери состояния. |
| Создание сессии успешно, промпт не отправлен | Сохранить ID созданной сессии и предложить восстановление без дублирования. |
| Нажатие «В работу» несколько раз | Одна операция на один запуск, блокировка на время выполнения. |
| MCP/skill для Redmine отсутствует | Список задач работает; после запуска показать/сохранить возможность явной диагностики агента. |
| Сессия удалена/архивирована после сохранения связи | Не давать невалидную ссылку «Открыть», показать недоступность. |
| Смена API-ключа на ключ другого пользователя | Изолировать пользовательские фильтры и сопоставления; сбросить чужой кэш задач. |

## 16. Безопасность и корпоративные ограничения

1. Ключ Redmine — **секрет**. Он не должен попадать в браузерные props/HTML, localStorage/sessionStorage, URL, логи, crash reports, analytics, prompt или результаты API, предназначенные UI.
2. Секреты хранить и использовать **только в доверенном контуре DSH Host**, используя штатное хранилище учётных данных там, где оно имеется.
3. Запросы к Redmine должны идти на заранее настроенный доверенный хост; не превращать параметр запроса/название задачи в произвольный URL для исходящего запроса.
4. Использовать HTTPS и проверку сертификатов; поддержку корпоративных CA настраивать, а не заменять отключением TLS.
5. Запись в Redmine новым плагином запрещена; технически проверять отсутствие write-запросов в тестах.
6. Не выводить в панель текст описаний, комментарии и вложения и не загружать их специально ради списка.
7. Если агент использует внешнюю LLM-модель, данные задачи могут покинуть корпоративный контур через **существующие MCP и model provider**. Плагин должен быть задокументирован с этим предупреждением; сам факт read-only доступа не означает разрешения на передачу данных во внешний LLM.
8. Применять обычные проверки доступа DSH при создании/открытии сессий; не обходить политики подтверждения операций агента.
9. Не допускать XSS/инъекций через названия задач, проектов, категории и прочие полученные из Redmine строки.
10. Удаление/замена API-ключа и отключение плагина должны иметь понятный эффект на локально сохранённые настройки; локальные DSH-проекты и сессии не удалять автоматически.

## 17. Нефункциональные требования

- **Нативность:** плагин подключается/отключается штатным способом, по возможности без правок исходников ядра DSH.
- **Стабильность:** ошибка Redmine не приводит к падению Web UI DSH и не блокирует работу обычных сессий.
- **Отзывчивость:** показывать загрузку сразу, не блокировать весь интерфейс ожиданием сети.
- **Масштабирование списка:** корректная работа с несколькими проектами и сотнями/тысячами доступных задач за счёт страниц, разумного количества запросов и предсказуемых ограничений поиска.
- **Актуальность:** обновление по кнопке действительно выполняет новый запрос, а не только меняет метку времени в UI.
- **Идемпотентность:** повторная регистрация того же workspace не создаёт дубли; повтор одного и того же события запуска не создаёт две сессии.
- **Совместимость:** поддержка корпоративного Redmine соответствующего 2022–2023 годам API, с проверкой по факту установки; не требовать новых функций без fallback.
- **ОС:** путь workspace обрабатывается средствами Host, с учётом Windows и других ОС, поддерживаемых конкретной инсталляцией DSH.
- **Доступность:** keyboard focus, доступные названия иконок, явные disabled/loading/error-состояния.
- **Наблюдаемость:** диагностические записи без секретов, достаточные для различения ошибки Redmine, workspace и создания сессии.
- **Тестируемость:** интеграционные сценарии должны проверяться без доступа к настоящему корпоративному ключу через тестовый/макетный Redmine API.

## 18. Критерии приёмки (Definition of Done)

### 18.1. Redmine и панель

- [ ] Плагин устанавливается как отдельное расширение в согласованной целевой версии DSH.
- [ ] Глобальная навигация содержит пункт Redmine, доступный без открытой DSH-сессии.
- [ ] URL + API-ключ настраиваются; тест соединения показывает действительного пользователя или объясняет ошибку.
- [ ] API-ключ не передаётся в браузер и не отображается в логах/промптах.
- [ ] После первого открытия отображаются задачи, **назначенные текущему пользователю**, в **доступных проектах**.
- [ ] По умолчанию статус — открытые; выбор «Все статусы» показывает также закрытые при наличии прав.
- [ ] Выпадающий список проектов включает режим «Все доступные», корректно обрабатывает много проектов и не теряет страницы API.
- [ ] Работают фильтры проектов, статусов, типов, приоритетов и применимых категорий.
- [ ] Работает поиск по ID/названию; его область не вводит пользователя в заблуждение.
- [ ] Работает сортировка и пагинация всего отфильтрованного набора.
- [ ] Состояние фильтров сохраняется при переходах по интерфейсу; «Сбросить» восстанавливает defaults.
- [ ] Кнопка `↻ Обновить` повторно запрашивает данные, показывает loading, сохраняет фильтры и workspace.
- [ ] При ошибке обновления прежняя информация остаётся видимой и помечается как устаревшая.
- [ ] В карточке нет тела описания, комментариев и истории; есть ссылка на исходную задачу в Redmine.
- [ ] Ни одна операция плагина не изменяет задачи Redmine.

### 18.2. Workspace и сессии

- [ ] «Выбрать/Изменить workspace» — **отдельная кнопка**, открывающая отдельный диалог.
- [ ] Диалог показывает существующие локальные проекты DSH с именами и путями.
- [ ] Диалог допускает выбор другой существующей директории Host-компьютера.
- [ ] Если директория уже зарегистрирована — использован существующий workspace (проект не продублирован).
- [ ] Если директория не зарегистрирована — после подтверждения она зарегистрирована как проект DSH.
- [ ] Каталог **не создаётся** на диске самим плагином.
- [ ] Привязка Redmine-проекта к DSH workspace может запоминаться, перепроверяется при повторном использовании и может переопределяться для отдельной задачи.
- [ ] Пока workspace не выбран/невалиден, «В работу» недоступна.
- [ ] «В работу» не запрашивает workspace повторно, если валидный выбор уже сделан.
- [ ] Каждое новое осознанное «В работу» создаёт **отдельную** DSH-сессию внутри выбранного DSH-проекта.
- [ ] Стартовый промпт сформирован из выбранного шаблона, содержит корректный URL/ID задачи и автоматически отправлен агенту.
- [ ] Созданная сессия открывается в интерфейсе DSH; при сохранённой сессии есть способ вернуться к ней.
- [ ] Двойной клик и сбой отправки промпта не порождают лишних сессий.
- [ ] При сбоях пользователь видит понятные сообщения и способы безопасного восстановления.

### 18.3. Проверка безопасности

- [ ] Автоматизированный тест/API-аудит подтверждает отсутствие `POST`/`PUT`/`PATCH`/`DELETE` запросов нового плагина к Redmine.
- [ ] Нет ключа в URL, локальном браузерном хранилище, промпте и UI-логах.
- [ ] UI экранирует полученные из Redmine строки, включая потенциально вредоносный текст.
- [ ] В документации явно отделено «плагин read-only» от возможных прав существующего агентного MCP.

## 19. Обязательные тестовые сценарии

1. Подключение с валидным ключом и с неверным ключом.
2. Redmine с изменёнными русскоязычными статусами и нестандартными trackers.
3. Много проектов, превышающих одну страницу ответа, в том числе проект без задач.
4. Задачи одного исполнителя в нескольких проектах; проверка «Все доступные» и выбора нескольких проектов.
5. Два проекта с одинаковыми именами категорий и разными category ID.
6. Открытые/закрытые задачи; сортировка и поиск с активными фильтрами.
7. Поиск названия на следующей странице: результат не теряется без предупреждения.
8. Ручное обновление после изменения задачи в тестовом Redmine; сохранение фильтров и выбранного workspace.
9. Ошибка/таймаут обновления при уже загруженном списке.
10. Выбор существующего workspace, повторный выбор той же директории и отсутствие дублей DSH-проектов.
11. Выбор новой **существующей** директории и её однократная регистрация.
12. Несуществующий путь, недоступная директория, файл вместо папки.
13. Сохранённый workspace, регистрация которого позже удалена в DSH.
14. Запуск задачи при валидном workspace: новая сессия в нужном проекте, правильный промпт, Redmine без изменений.
15. Запуск той же задачи второй раз намеренно; отдельная новая сессия.
16. Двойной клик по «В работу»: одна сессия.
17. Ошибка после создания сессии, но до отправки промпта: восстановление без дубля.
18. Смена учётной записи Redmine через новый ключ: чужие фильтры, кэш и маппинги не используются.
19. Удалённая/архивированная сессия в истории связи задачи: интерфейс не ведёт на несуществующую сессию.
20. Проверка читающего HTTP-трафика, отсутствия утечки API-ключа и корректного TLS.

## 21. Открытые технические вопросы — исследовать, но не менять продуктовую концепцию

1. Какая **точная версия/коммит** DSH будет целевым? Соответствуют ли его реальные UI slots и workspace/session APIs актуальным документам?
2. Какой штатный путь **директорного пикера** доступен в Web UI/на используемой ОС? Когда браузер и DSH Host на разных машинах, выбирается каталог именно Host.
3. Какая **точная версия** корпоративного Redmine и какие права REST API выданы ключу?
4. Какие серверные операторы доступны для объединения нескольких проектов, статусов, приоритетов и категорий; как обеспечить корректные фильтры/поиск без ложной полноты?
5. Есть ли корректное безопасное хранилище секретов в целевой сборке DSH и механизм user-scoped настроек?
6. Поддерживает ли выбранная сборка штатную маршрутизацию к новой сессии после её создания и подтверждение фактической отправки первого сообщения?
7. Можно ли административно ограничить **существующий Redmine MCP** только читающими инструментами для строгого выполнения корпоративного требования read-only в агентной части?

На перечисленные вопросы агент должен ответить **на этапе исследования** и документировать найденные ограничения. Если API отличается, адаптировать технический подход, **сохраняя согласованное поведение пользователя**. Если какое-то обязательное поведение объективно недостижимо, не симулировать успех: оформить явный блокер и предложить наименьшее возможное изменение UX.

## 22. Краткие продуктовые решения, которые нельзя потерять

1. Плагин **не дублирует Redmine**: полноценный текст/комментарии пользователь читает в браузере, агент — существующими MCP/skill.
2. **Только назначенные мне задачи по умолчанию**, из **всех доступных проектов**, с гибкими фильтрами.
3. Есть большая понятная **кнопка ручного обновления с круговой стрелкой**.
4. **Workspace выбирается отдельной кнопкой** и в отдельном диалоге; можно выбрать уже зарегистрированный проект DSH либо другую существующую директорию.
5. **Если путь уже зарегистрирован, ничего не создавать**; иначе **регистрировать локальный проект DSH** по выбранному существующему каталогу.
6. **«В работу» — отдельная кнопка**, создающая **новую сессию в выбранном DSH-проекте**, с автоматической отправкой настраиваемого промпта и URL задачи.
7. Сохранять соответствия Redmine-проектов и локальных workspace, но разрешать переопределение для задачи.
8. Плагин **никогда не меняет данные Redmine**. Не путать «В работу» в интерфейсе DSH со статусом «В работе» в Redmine.
9. Максимально использовать **родные возможности DSH**, не создавать свой менеджер проектов/сессий.
10. Совместимость с Redmine примерно **2022–2023 гг.**, без предположения о точном релизе и доступности новых API.
